# Кастомный транспорт для NestJS & Kafka

NestJS - очень популярный фреймворк для создания бэкенда на TypeScript. Этот фреймворк отлично подходит для создания проектов различной сложности и сегодня мы поговорим о больших проектах на базе микросервисной архитектуры. В интернете можно найти много различных материалов, в которых подробно раскрываются преимущества и недостатки микросервисной архитектуры, но в этой статье мы сфокусируемся на технической реализации с примерами. Вы можете скачать полностью функционирующий пример статьи из [публичного репозитория](https://github.com/quazex/nestjs-learning), в котором можно найти массу других полезных материалов для знакомства с подходами в работе с NestJS.

## Введение

Основная цель статьи заключается в демонстрации эффективных подходов при решении задач, которые выходят за рамки готовых решений. Отличной точкой старта можно считать знакомство с [официальной документацией](https://docs.nestjs.com/microservices/custom-transport), описывающей базовые подходы при создании транспорта для `@nestjs/microservices`. Также, будет крайне важно изучить ключевые концепты при работе с Kafka.


## Задача

Давайте представим, что нам необходимо создать сервис для получения потока различных данных из Kafka и сохранения пачки данных в [ClickHouse](https://github.com/quazex/nestjs-clickhouse) для формирования статистики. Такая комбинация технологий отлично дополняет друг друга, потому что ClickHouse наиболее эффективен при вставке данных большими пачками, а Kafka помогает обеспечить такую доставку надежно. Учитывая условия, нам необходимо получать множество сообщений за один раз, при этом допускается публикация сообщений как пачками, так и поштучно.

## Мотивация
Почему мы будем создавать собственное решение вместо использования готового? Такой подход имеет ряд преимуществ и мы кратко рассмотрим каждое:
1. Наша задача заметно отличается от подходов в базовой интеграции с Kafka в пакете `@nestjs/microservices` (судя по исходному коду [KafkaServer](https://github.com/nestjs/nest/blob/master/packages/microservices/server/server-kafka.ts#L172) мы не можем настроить получение сообщений батчами);
1. Нам важно иметь бóльший контроль зависимостей для большей гибкости в будущем. На момент создания статьи доступно не так много клиентов для интеграции с Kafka, при этом в каждом есть свои заметные недостатки. Например, популярная библиотека [kafkajs](https://github.com/tulios/kafkajs) последний раз обновлялась два года назад, а [node-rdkafka](https://github.com/Blizzard/node-rdkafka) основана на [librdkafka](librdkafka), что может вызывать трудности при запуске проекта на различных платформах;
1. Мы хотим иметь доступ к экземпляру подключения для Health Check проверок (UPD: в версии 11.x `@nestjs/microservices` [появилась такая возможность](https://docs.nestjs.com/microservices/basics#underlying-driver-access)). Таким образом мы можем точно определить состояние подключения для принятия решений;
1. Гибкость при настройке логирования;
1. Возможность создать относительно простое решение под конкретную задачу, что повысит надежность и упростит будущую поддержку.

## Реализация
После знакомства с основами мы готовы приступить к созданию типового модуля для NestJS с динамической конфигурацией. Единственное отличие будет заключаться в классе, который мы будем использовать в `main.ts` для подключения к Kafka в рамках микросервисной архитектуры.

Наш модуль будет включать в себя два ключевых компонента: продюсер и консюмер сообщений. Также, в рамках задачи нам важно иметь возможность гибкой смены клиента для интеграции с  Kafka, поэтому мы будем стремиться к изолированию элементов `kafkajs` в каждом компоненте. Такой подход позволит скрыть детали реализации и при потенциальной смене клиента избежать дополнительных доработок в рамках микросервиса, который использует наш модуль. Дополнительно, в каждый компонент мы добавим провайдер с Health Check проверкой подключений.

С подробным рабочим примером вы можете ознакомиться в репозитории
В структуру модуля входят файлы в разрезе каждого компонента:

```bash
consumer/
    consumer.context.ts       # Настройка доступа к дополнительным полям запроса
    consumer.decorators.ts    # Декораторы на базе @Inject для доступа к клиентам
    consumer.indicator.ts     # Проверка подключения консюмера
    consumer.interfaces.ts    # Типы для динамической конфигурации модуля
    consumer.module.ts        # Модуль консюмера и его инициализация
    consumer.pattern.ts       # Обертка для EventPattern с явным указанием транспорта
    consumer.providers.ts     # Набор фабрик для генерации Injactable провайдеров
    consumer.strategy.ts      # Сервер подписки и обработки входящих данных
    consumer.tokens.ts        # Уникальные токены для управления компонентами модуля
    consumer.transport.ts     # Идентификатор транспорта для разделения подписок
    consumer.types.ts         # Различные типы

producer/
    producer.client.ts        # Клиент для рассылки
    producer.decorators.ts    # Декораторы на базе @Inject для доступа к клиентам
    producer.indicator.ts     # Проверка подключения продюсера
    producer.interfaces.ts    # Типы для динамической конфигурации модуля
    producer.module.ts        # Модуль продюсера и его инициализация
    producer.providers.ts     # Набор фабрик для генерации Injactable провайдеров
    producer.tokens.ts        # Уникальные токены для управления компонентами модуля
    producer.types.ts         # Различные типы

shared/
    shared.logger.ts          # Кастомный логгер для kafkajs на базе NestJS логгера
    shared.payload.ts         # Универсальный конвертер данных сообщения
```

## Продюсер

Основным файлом нашего компонента продюсера является файл `producer.client.ts`, который содержит провайдер для отправки сообщений в Kafka. Мы намеренно выбрали базовую реализацию клиента без наследования от `ClientProxy` чтобы порадовать сторонников принципа KISS, тем более официальная документация [допускает](https://docs.nestjs.com/microservices/custom-transport#client-proxy) подобный подход.

## Консюмер

Компонент консюмера реализован более комплексно, потому что нам необходимо настроить интеграцию с модулем `@nestjs/microservices` с учетом ряда факторов:

- [CustomTransportStrategy](https://docs.nestjs.com/microservices/custom-transport#creating-a-strategy) содержит реализацию подключения и подписки;
- [BaseRpcContext](https://docs.nestjs.com/microservices/basics#additional-request-details) для гибкого управления доступа к исходному запросу, полезно использовать в контроллерах и интерцепторах;
- [EventPattern](https://docs.nestjs.com/microservices/basics#event-based) для подписки на определенный топик с предварительно настроенным идентификатором транспорта;
- [TransportId](https://github.com/nestjs/nest/blob/1775756bbeca1a3a0c4b5d8d7e453f497051cb32/packages/microservices/interfaces/custom-transport-strategy.interface.ts#L10) чтобы наши декораторы не смешивались с базовыми EventPattern;

## Реализация

В нашем примере мы запустим продюсер и консюмер в одном приложении для удобства тестирования. Конечно, в реальных проектах это будут разные сервисы, но подходы останутся такими же. Несмотря на базовую реализацию, нам пример имеет ряд интересных особенностей:

- Мы поднимаем Kafka в Docker контейнере перед запуском тестов и останавливаем его после их окончания;
- Пример демонстрирует применение привычного DTO (хотя декоратор кастомный, но только для простоты использования стандартных подходов валидации);
- Применяется кастомный Interceptor без дополнительных настроек;
- В интерцепторе содержится пример использования контекста подписки (заодно можно наглядно оценить преимущества и контекста запроса);
- Отдельный тест-кейс наглядно показывает работа с подключениями для реализации Health Check стратегии.

## Заключение

Таким образом, мы получили довольно базовый вариант кастомного транспорта на базе `@nestjs/microservices`. Итоговый вариант гармонично вписывается в подходы фреймворка NestJS, позволяет создавать переиспользуемые Interceptors и DTO без жесткой привязки к конкретной реализации транспорта (Interceptor в примере завязан на конкретную реализацию контекста, но мы легко можем обратить такую зависимость через интерфейс). Вы можете самостоятельно изучить работу модуля, запуская тесты с дебаггером (конфигурация для VSCode включена в проект).
